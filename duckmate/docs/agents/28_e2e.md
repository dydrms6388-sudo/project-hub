## 다음 에이전트에게 넘기는 결정사항

### 판단 확정

| # | 쟁점 | 확정 | 근거 |
|---|---|---|---|
| **G1-1** | 실행 환경 | E2E 는 **살아 있는 Supabase 인스턴스 전제**. 모킹하지 않는다 | 가입·RLS·매칭·마스킹이 전부 DB/Edge Function 소관이라 모킹하면 검증 대상이 사라진다. 대신 미구성 환경에서는 **실패가 아니라 skip** 으로 떨어뜨려 "환경 미구성"과 "회귀"를 리포트에서 분리한다 |
| **G1-2** | 본인인증 | `IDENTITY_VERIFIER=stub` 고정. 휴대폰 OTP 는 **아무 6자리**(`123456`)로 통과 | `onboarding/phone/actions.ts` 가 stub 이 아니면 `VERIFIER_NOT_CONFIGURED` 로 잠그고, StubVerifier 는 코드 검증 없이 성공한다. 실 OTP 는 SMS 어댑터 도입(D2 미결 2) 후 시나리오 교체 |
| **G1-3** | 설정 로드 실패 금지 | `playwright.config.ts` 는 env 를 **단언하지 않는다** | `playwright test --list` 를 Supabase 없는 CI 스테이지의 문법·수집 게이트로 쓰기 위함. 사전조건 검사는 `e2e/helpers/env.ts` 가 런타임에 수행 |
| **G1-4** | 브라우저 설치 | `playwright install` 을 **실행하지 않는다**. `PLAYWRIGHT_BROWSERS_PATH` 로 기설치 경로를 주입 | 이 세션/CI 이미지에 이미 chromium 이 있다(`/opt/pw-browsers`). 설치 단계를 넣으면 오프라인 러너에서 깨진다 |
| **G1-5** | 추천 큐 확보 | 계정 2개 생성 직후 **Edge Function `daily-recommendations` 를 service role 로 직접 호출**해 오늘자 큐를 재발행 | `/discover` 는 `daily_recommendations` 행이 있어야 카드를 그린다. cron(KST 06:00)을 기다릴 수 없다. 호출 경로가 없으면 매칭 스펙 전체 skip |
| **G1-6** | 매칭 성립 조건 | 두 계정 모두 `/verify` 스텁으로 **Lv2 승급 후** 상호 좋아요 | Lv1 상호 좋아요는 매칭이 아니라 **보류**(§8.5)다. Lv2 미승급이면 `pending` 이 나오고 채팅이 열리지 않는다 |
| **G1-7** | 셀렉터 정책 | E1(가입·온보딩)·E3(채팅)은 `data-testid`, **E2(home·discover·likes)·E4(me·settings·verify·legal)는 role/텍스트** | 후자에는 `data-testid` 가 **하나도 없다**(실측). 텍스트 셀렉터는 카피 변경에 깨지므로 담당 에이전트가 testid 를 붙여야 한다 → §미결 1 |
| **G1-8** | 화면 파일 무수정 | 테스트를 통과시키려고 화면 파일을 고치지 않았다 | 파일 소유권 규약. 필요한 변경은 전부 §미결 에 담당 에이전트 지정으로 기록 |
| **G1-9** | 테스트 계정 격리 | 이메일 = `dm-e2e-<label>-<token>@e2e.duckmate.invalid` (RFC 6761 예약 TLD) | 운영 DB 에 섞여도 `email like 'dm-e2e-%'` 로 일괄 식별·정리 가능. 실 도메인으로 메일이 나갈 경로가 없다 |
| **G1-10** | 산출물 경로 | `playwright-report/` · `test-results/` (루트 `.gitignore` 가 이미 무시하는 이름) | `.gitignore` 는 G1 소유 파일이 아니라 수정하지 않았다 |

### → 각 담당 에이전트에게 넘기는 요청

1. **E2 (home·discover·likes)**: `data-testid` 부재. 최소 `discover-card`, `discover-like`, `discover-pass`, `discover-superlike`, `match-reveal`, `match-reveal-suggestion`, `likes-count`, `home-verify-cta` 를 붙여 주면 `e2e/helpers/selectors.ts` 의 `ROLE` 블록을 `TID` 로 옮길 수 있다.
2. **E4 (me·settings·verify)**: `verify-start`, `verify-level`, `settings-mode`, `settings-delete` 등. 특히 `/verify` 의 시작 버튼은 지금 **버튼 텍스트("본인인증 시작하기")로만 잡힌다** — 카피가 바뀌면 매칭 스펙 전체가 죽는다.
3. **D3 (매칭)**: 신규 가입 2인이 서로의 추천 큐에 확실히 들어오는지가 알고리즘 종속이다. E2E 전용 결정성 확보 수단(예: `build_daily_recommendations(for_date, p_only_profiles uuid[])` 인자 추가)이 있으면 §미결 2 가 해소된다.
4. **G2 (보안 리뷰)**: `IDENTITY_VERIFIER=stub` 이 프로덕션 env 로 새면 본인인증이 무조건 통과한다. 배포 파이프라인에서 이 값이 production 에 존재하지 않는지 확인하는 가드가 필요하다(현재는 런타임 `console.warn` 1회뿐).
5. **G3 (CI)**: 아래 §5 의 2단 파이프라인(수집 게이트 / 전체 실행)을 워크플로로 옮길 것.

## 3. 사전조건 (실제 실행에 필요한 것)

| # | 항목 | 값 / 방법 | 없으면 |
|---|---|---|---|
| 1 | Supabase 인스턴스 | 로컬 `supabase start` 또는 전용 스테이징 프로젝트. `supabase/migrations/00001~00013` 전부 적용 + `00005_seed.sql`(취미 태그·퀴즈 10문항) | 전 스펙 skip (legal/age-gate 제외) |
| 2 | 앱 env | `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 동일 |
| 3 | 인증 스텁 | `IDENTITY_VERIFIER=stub` — **프로덕션 env 에는 절대 넣지 말 것** | 휴대폰 스텝에서 `VERIFIER_NOT_CONFIGURED` |
| 4 | 이메일 확인 끄기 | Supabase Auth → **Confirm email = OFF**. 확인했다는 표시로 `E2E_SUPABASE_EMAIL_CONFIRM=off` | 가입 직후 세션이 없어 `/login` 으로 튕김 → 온보딩 진행 불가 |
| 5 | 서비스 키 | `SUPABASE_SERVICE_ROLE_KEY` (+ 필요 시 `E2E_SUPABASE_FUNCTIONS_URL`). Edge Function `daily-recommendations` 가 배포/서브되어 있어야 함 | matching-chat 전체 skip |
| 6 | 브라우저 | `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers` (기설치 chromium). `playwright install` 금지 | 브라우저 미발견 오류 |
| 7 | 계정 2개 | 스펙이 **매 실행마다 새로 만든다**(고정 계정 없음). 사전 준비 불필요, 대신 실행마다 DB 에 계정이 쌓인다 | — |

### 선택 env

| 이름 | 기본값 | 용도 |
|---|---|---|
| `E2E_BASE_URL` | (없음) | 지정 시 dev 서버를 띄우지 않고 그 URL 을 대상으로 실행(프리뷰 배포 검증) |
| `E2E_PORT` | `3000` | 로컬 dev 서버 포트 |
| `E2E_WORKERS` | `1` | 로컬 워커 수 |

### 테스트 데이터 정리

실행마다 계정이 누적된다. 스테이징에서 주기적으로:

```sql
-- 확인 후 실행할 것. auth.users 삭제 시 profiles 는 cascade 로 정리된다.
select id, email from auth.users where email like 'dm-e2e-%@e2e.duckmate.invalid';
```

> 운영 DB 에서는 절대 돌리지 말 것. E2E 는 **전용 프로젝트에서만** 실행한다(계정·좋아요·신고 행이 실제로 쌓인다).

## 4. 실행 방법

### 4.1 문법·수집 검증만 (Supabase 불필요 — 지금 이 저장소에서 가능)

```bash
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers \
  pnpm --filter @duckmate/web exec playwright test --list
```

기대: `Total: 34 tests in 4 files` (chromium 25 + mobile-chrome 9).

### 4.2 로컬 Supabase 로 전체 실행

```bash
# 1) DB 기동 + 마이그레이션/시드
supabase start
supabase db reset          # 00001~00013 + 00005 시드

# 2) Auth 설정: Confirm email OFF (Studio → Authentication → Providers → Email)

# 3) Edge Function 서브
supabase functions serve daily-recommendations --no-verify-jwt &

# 4) env (.env.local)
#   NEXT_PUBLIC_SUPABASE_URL / NEXT_PUBLIC_SUPABASE_ANON_KEY / SUPABASE_SERVICE_ROLE_KEY
#   IDENTITY_VERIFIER=stub
#   E2E_SUPABASE_EMAIL_CONFIRM=off
#   E2E_SUPABASE_FUNCTIONS_URL=http://127.0.0.1:54321/functions/v1

# 5) 실행 (webServer 가 pnpm dev 를 :3000 에 자동 기동)
PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers \
  pnpm --filter @duckmate/web exec playwright test
```

단일 스펙: `... playwright test e2e/age-gate.spec.ts --project=chromium`
UI 모드: `... playwright test --ui` / 트레이스: `... playwright show-trace test-results/**/trace.zip`

### 4.3 프로덕션(스테이징) 배포 대상 실행

```bash
E2E_BASE_URL=https://staging.duckmate.example.com \
NEXT_PUBLIC_SUPABASE_URL=... NEXT_PUBLIC_SUPABASE_ANON_KEY=... \
SUPABASE_SERVICE_ROLE_KEY=... IDENTITY_VERIFIER=stub \
PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers \
  pnpm --filter @duckmate/web exec playwright test
```

- `E2E_BASE_URL` 이 있으면 `webServer` 를 띄우지 않는다.
- **대상 배포에도 `IDENTITY_VERIFIER=stub` 이 켜져 있어야** 휴대폰/본인인증 스텝이 통과한다 → 그래서 **실서비스 프로젝트를 대상으로 돌리면 안 된다.** 전용 스테이징만 사용.
- 대안(스텁 없이): `REVIEW_BYPASS_EMAILS` 화이트리스트에 테스트 계정 이메일을 넣으면 그 계정만 Stub 경로를 탄다(B3 R2). 단 계정 이메일이 실행마다 랜덤이라 현재 스펙과는 맞지 않는다 — 고정 계정 모드가 필요하면 §미결 4.

## 6. 셀렉터 규약 요약

### 6.1 원칙

1. **`data-testid` 최우선.** 없으면 `getByRole(role, { name })`, 최후에 텍스트.
2. 테스트는 화면 파일을 고치지 않는다. testid 가 필요하면 담당 에이전트에게 요청한다(§미결 1).
3. 동적 id(취미 UUID, 매치 UUID)는 상수화하지 않고 **접두 매칭**(`[data-testid^="hobby-chip-"]`) 또는 **data 속성**(`data-match-id`, `data-code`)으로 잡는다.
4. 상태는 클래스가 아니라 **데이터 속성**으로 읽는다: 신고 시트 단계 = `data-step`, 말풍선 주인 = `data-mine`.

### 6.2 화면별 현황 (실측)

| 그룹 | 화면 | testid | 대표 셀렉터 |
|---|---|---|---|
| E1 | `(auth)/signup`, `(auth)/login` | ✅ 촘촘 | `signup-form`, `signup-birth-year`, `consent-terms`, `age-denied` |
| E1 | `onboarding/*` | ✅ 촘촘 | `onboarding-step-<step>`, `onboarding-step-count`, `phone-stub-notice`, `hobby-chip-<uuid>`, `quiz-option-<0..3>`, `duckcard-skip`, `photo-skip`, `mode-radio-friend` |
| E3 | `(main)/chat/**` | ✅ 촘촘 | `chat-room[data-match-id]`, `chat-message[data-mine]`, `chat-composer-input`, `chat-menu-report`, `chat-report-sheet[data-step]`, `chat-report-reason[data-code]` |
| **E2** | `(main)/home`, `discover`, `likes` | ❌ **0개** | `getByRole("button", { name: "<닉네임>님에게 좋아요 보내기" })` 등 aria-label 의존 |
| **E4** | `(main)/me`, `settings`, `verify`, `app/legal` | ❌ **0개** | 버튼 텍스트("본인인증 시작하기"), `a[href="/legal/terms"]` |

공통 규약: 폼 에러는 어느 화면이든 `data-testid="form-error"` (role=alert).

## 7. 현재 실행 불가 사유와 해소 조건

### 7.1 현 상태 (G1 세션 기준)

| 항목 | 상태 |
|---|---|
| 테스트 수집 (`--list`) | ✅ **검증 완료** — 34개 테스트 / 4개 파일 정상 수집 |
| 타입 체크 (`tsc --noEmit`) | ✅ 통과 (e2e/** 포함) |
| 실제 브라우저 실행 | ❌ **불가** |

### 7.2 불가 사유

1. **Supabase 인스턴스가 이 세션에 없다.** 프로덕션·로컬 어느 쪽도 붙어 있지 않고, `supabase` CLI 로 로컬 스택을 띄울 권한/컨테이너도 없다. 가입(`supabase.auth.signUp`)이 네트워크 단계에서 실패하므로 온보딩·매칭·채팅·신고 스펙은 한 줄도 진행되지 않는다.
2. **`.env` 미구성.** `.env.example` 의 값은 전부 플레이스홀더(`YOUR_...`)다. `helpers/env.ts` 가 이를 감지해 계정이 필요한 스펙을 skip 한다.
3. **`IDENTITY_VERIFIER` 미설정.** 설정돼 있어도 1이 해소되지 않으면 의미 없다.
4. **Edge Function 미서브.** `daily-recommendations` 가 없어 `/discover` 큐가 비어 있다.
5. 부수적으로 `legal-pages.spec.ts` · `age-gate.spec.ts` 는 **백엔드가 필요 없다** — dev 서버만 뜨면 돌아간다. 다만 dev 서버 기동(`next dev`)은 `middleware.ts` 가 `NEXT_PUBLIC_SUPABASE_URL!` 을 non-null 단언으로 읽어 **요청 시점에 터진다**. 즉 값이 형식만 맞으면(더미 URL + 더미 키) 이 두 스펙은 통과 가능하다 → §미결 5.

### 7.3 해소 조건 (체크리스트)

- [ ] 전용 Supabase 프로젝트(또는 로컬 `supabase start`) 확보 + `db reset` 으로 00001~00013 + 시드 적용
- [ ] Auth 설정에서 **Confirm email OFF**
- [ ] `.env.local` 에 URL/anon/service-role + `IDENTITY_VERIFIER=stub` + `E2E_SUPABASE_EMAIL_CONFIRM=off`
- [ ] `supabase functions serve daily-recommendations` (또는 배포)
- [ ] `PLAYWRIGHT_BROWSERS_PATH` 지정 후 `playwright test`

위 5개가 충족되는 순간 §4.2 명령 그대로 전체 스펙이 돌아간다. 코드 변경은 필요 없다.

## 8. 미결 사항 (담당 지정)

| # | 사안 | 담당 | 내용 |
|---|---|---|---|
| 1 | **E2·E4 화면에 `data-testid` 없음** | E2 / E4 | 현재 좋아요 버튼은 `aria-label="<닉네임>님에게 좋아요 보내기"`, 인증 시작은 버튼 텍스트로만 잡힌다. 카피 한 줄 바꾸면 매칭 스펙 전체가 죽는다. §결정-1·2 의 testid 목록 추가 요청 |
| 2 | **매칭 결정성** | D3 | 신규 2인이 서로의 오늘자 추천 큐에 반드시 들어간다는 보장이 없다. 현재 스펙은 큐에서 상대를 못 찾으면 `test.skip` 으로 빠진다(거짓 성공 방지). `build_daily_recommendations` 에 대상 프로필 한정 인자가 생기면 확정 검증으로 승격 |
| 3 | **`OTHER` 사유 상세 필수 검증** | G1(후속) | 신고 시트는 라우트가 아니라 대화방 안에만 존재해 별도 매칭 쌍이 필요하다. 매칭 쌍 2개를 만드는 픽스처가 생기면 추가 |
| 4 | **고정 계정 모드** | G3 | 스테이징에서 `REVIEW_BYPASS_EMAILS` 로 스텁 없이 돌리려면 계정이 고정이어야 한다. `E2E_FIXED_ACCOUNT_A/B` env 를 읽는 모드 추가 여부 결정 필요 |
| 5 | **더미 env 로 dev 서버 기동** | E그룹/오케스트레이터 | `middleware.ts` 가 Supabase env 를 non-null 단언한다. 값이 없으면 모든 요청이 500 이라, 백엔드 불필요한 legal/age-gate 스펙조차 "형식만 맞는 더미 값"을 요구한다. 미설정 시 우아하게 통과시킬지(공개 경로 한정) 판단 필요 — **G1 은 middleware 를 수정하지 않았다** |
| 6 | **마스킹 해제(72h) · 제재 · 이의제기 시나리오** | G3 | 시간 경과·관리자 조치가 필요해 브라우저 E2E 범위 밖. 서버 테스트 또는 시간 주입 픽스처 필요 |
| 7 | **접근성 자동 검증** | G3 | axe 계열 도구는 새 의존성이라 도입하지 않았다(기술 제약). 필요하면 승인 후 `@axe-core/playwright` 추가 |
