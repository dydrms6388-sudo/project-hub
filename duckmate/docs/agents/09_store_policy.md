### 2. E4 (프로필/설정/구독 UI) — 화면 분기 규칙 [Phase 3 구현부터 적용]

| # | 규칙 | 이유 |
|---|---|---|
| E-1 | 플랫폼 판별 유틸 `getRuntime(): 'web' \| 'ios' \| 'android'` 를 지금 만들고(웹에서는 항상 `web` 반환), **결제·구독 관련 모든 화면은 이 유틸로 분기**한다. Capacitor 도입 시 `Capacitor.getPlatform()` 연결만 추가 | Phase 4에서 화면별 if 문을 새로 심는 대참사 방지 |
| E-2 | 구독 관리 화면: 해지·환불 버튼은 `provider.capabilities` 기반 렌더. IAP 구독은 "해지" = 스토어 구독 설정 **딥링크**(`manageSubscriptionUrl()`), 앱 내 자체 해지 폼 미노출. 웹 Toss 구독은 기존 2뎁스 해지 유지 | 04 §6.2. IAP 갱신·해지는 스토어가 관리 |
| E-3 | 환불 신청 폼(F-PAY-05)은 `provider=toss` 결제 건에만 노출. IAP 건은 스토어 환불 안내 링크로 대체 | 우리 `calc_refund()`는 웹 결제 전용(04 §7) |
| E-4 | 페이월·구독 화면에 외부 URL로 나가는 링크(회사 사이트 요금 안내 포함) 배치 금지. 법적 고지(약관·개인정보) 링크는 인앱 웹뷰로 열되 **결제 화면에서 요금 페이지로의 동선은 두지 않는다** | 3.1.1 anti-steering. 예외 국가 대응은 Phase 4에서 별도 결정(본문 3절) |
| E-5 | 설정 화면에 **계정 삭제(탈퇴) 진입점을 2뎁스 이내 상시 노출**(F-PRF-03과 동일 항목). "문의하세요" 식 간접 삭제 금지 | Apple 5.1.1(v)·Google 계정 삭제 정책 — 앱 심사 필수 항목 |
| E-6 | 알림 설정 화면은 푸시 권한 상태를 읽어 표시하는 구조로 작성(권한 미허용 시 OS 설정 딥링크 버튼). Web Push 권한 로직을 `PushAdapter` 뒤로 숨긴다 | Phase 4 FCM/APNs 전환(F-NTF-04) 시 화면 무수정 |

### 3. 전 에이전트 공통 — 스토어 심사를 전제로 Phase 1~3에서 지킬 것

1. **신고·차단은 2탭 상시 노출 유지**(A5·PRD F-SAF-05). Apple 1.2 / Google UGC 정책의 핵심 증빙이며, 심사 스크린샷 대상이다. 절대 뎁스를 늘리지 말 것.
2. **연령 게이트(만 19세)·본인인증 플로우는 심사원 데모 계정이 통과 가능해야 한다**: D2는 `IdentityVerifier` 스텁에 **심사용 바이패스 계정(서버 화이트리스트, 프로덕션 env 플래그)** 경로를 Phase 1부터 설계에 포함(본문 4절 준비물).
3. **수집 데이터 목록의 단일 소스**: D1은 개인정보 항목(수집 필드·목적·보존기간)을 `packages/db` 주석 또는 `docs/` 표로 유지 — Apple 개인정보 라벨·Google 데이터 안전 폼을 여기서 그대로 전사한다(본문 4.3).
4. **딥링크 스킴 예약**: `duckmate://` (커스텀) + `https://{도메인}/…` Universal Links/App Links. E1~E4는 공유·인증 콜백·푸시 랜딩 URL을 전부 **상대경로 라우트 기준**으로 작성(본문 5절).
5. **콘텐츠 등급 전제 = 성인(만 19세+) 데이팅 앱**: Apple 17+(신등급 체계 시 18+), Google Mature/IARC 성인 등급. 마케팅 카피·스토어 스크린샷에 선정적 소재 금지 — C1 톤 가이드와 정합.

## 1. Apple App Store 검토

### 1.1 Guideline 4.3 — 스팸/중복 앱 (Capacitor 웹뷰 래핑 리스크) — **리스크 High**

| 항목 | 내용 |
|---|---|
| 규정 요지 | ① 4.3(a): 단순 웹사이트 재포장("repackaged website") 앱 리젝. ② 4.3(b): **데이팅은 명시된 포화 카테고리** — "unique, high-quality experience"가 없으면 리젝. 데이팅 앱은 이중으로 걸린다. |
| 덕메이트 리스크 | Capacitor = 웹뷰 래핑이므로 "웹사이트를 앱으로 포장했다"는 판정 가능성이 구조적으로 존재. 최소 기능(4.2 Minimum Functionality)도 함께 심사됨. |
| 대응 — 네이티브 기능 요건 | 심사원이 체감할 **네이티브 통합을 최소 4종** 탑재: ① 푸시 알림(FCM/APNs — 스펙 §2 확정) ② 딥링크/Universal Links ③ IAP(그 자체가 네이티브 통합 증빙) ④ 카메라/사진 라이브러리 네이티브 피커(프로필 사진 업로드) + 생체인증(앱 잠금, 선택). 오프라인 스플래시·네이티브 전환 애니메이션·햅틱(매칭 리빌)도 가산점. |
| 대응 — 차별성 소명 | App Review 노트에 "외모 스와이프가 아닌 취미 궁합 매칭"(PRD §1 가치 제안 4개)과 안전장치(24h SLA, 미인증 DM 불가)를 명시 — 포화 카테고리 방어 논리. |
| 잔여 리스크 | 그래도 4.3 리젝 시: Resolution Center에서 차별성·네이티브 기능 목록으로 어필 → 재제출. 최악 시 주요 화면 일부의 네이티브 셸 강화 필요(예산 이슈 → 소유자 보고). |

### 1.3 데이팅 카테고리 특수 심사 — 1.2 UGC 안전장치 — **리스크 Med (준비물로 낮출 수 있음)**

### 1.4 연령 등급 — **리스크 Low**

- 데이팅 앱은 종전 체계 기준 **17+** 고정. Apple이 2025년 발표한 신등급 체계(4+/9+/13+/16+/18+) 적용 시 **18+** — 성인 전용(만 19세) 정책과 자연 정합.
- Made for Kids 아님, 연령 스크리닝은 앱 자체 게이트(3중 연령 게이트)로 소명.
- ⚠️ Phase 4 재확인: 신등급 설문 항목(데이팅/성적 콘텐츠/UGC 빈도).

### 3.2 웹 결제 유도 금지 조항이 만드는 운영 규칙

| # | 규칙 | 적용 대상 |

| W-7 | 업/다운그레이드는 **결제한 채널에서만** 가능(타 채널에서는 안내만). IAP 구독 변경은 스토어 구독 그룹으로 처리 | D6, E4 |

```
apps/web/lib/payments/toss.ts          ← Phase 3: TossProvider 구현
apps/web/lib/payments/iap.ts           ← Phase 4: IapProvider (RevenueCat) 구현
apps/web/lib/payments/index.ts         ← getRuntime() 기반 provider 선택 팩토리 (Phase 3부터 존재)
```

- 서버측: 웹훅 수신 → 검증 → `subscriptions`/`item_ledger` 갱신 파이프라인을 **provider-agnostic 공통 함수**로(결정사항 P-5). RevenueCat 웹훅 엔드포인트는 Phase 4에 어댑터만 추가.
- E2E(G1): Phase 3에 "결제 화면이 provider 팩토리를 경유한다" 스모크 1개 추가 — Phase 4 회귀 방지 앵커.

### 5.4 웹뷰 결제 화면 분기 (결정사항 E-1~E-4 상세)

| 화면 | `web` 런타임 | `ios`/`android` 런타임 |
|---|---|---|
| 페이월 시트 | Toss 결제 진입 버튼 + 웹 가격 | IAP 구매 버튼 + 스토어 가격(`getProducts()` 실시간) |
